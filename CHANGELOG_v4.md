# CHANGELOG v4

Эта версия основана на реальных данных, которые раньше не были доступны:
твой `db-backup-20260803-134623.zip` (реальная БД бота с данными, не
только структура), прямой просмотр vpnonline.su и README форка бота
(evansvl/vless-shopbot, тот же движок, что и bilbo111/3xui-shopbot).
Всё ниже — то, что реально проверено по этим источникам, с явной пометкой
там, где осталось допущение.

## 1. Критическая находка: в приложении не было экрана входа

`ApiClient` создавался заново на каждом экране (`final _api = ApiClient();`
в menu/plans/keys/servers/referral/connect), нигде не было ни одного
`setToken(...)`, а `main.dart` открывал `RootShell` сразу после
онбординга. Итог: токен был `null` абсолютно везде, каждый запрос к
защищённым эндпоинтам получал бы 401. **Весь функционал синхронизации не
мог работать физически**, несмотря на готовый backend.

Исправлено:
- `screens/auth_screen.dart` — вход / регистрация / сброс пароля, 1:1 по
  реальному сайту.
- `services/api_client.dart` — единственный на всё приложение синглтон
  `ApiClient.instance`, токен хранится в `flutter_secure_storage`
  (Keychain/Keystore/Credential Manager), восстанавливается при старте.
- `main.dart` — реальный граф состояний: онбординг → проверка сессии →
  вход (если нет токена) → приложение.
- `menu_screen.dart` — кнопка "Выйти" была `onPressed: () {}`, теперь
  реально чистит токен.

## 2. Критическая находка: `vpn_keys.host_name` — не то, чем казалось

Проверено прямым SQL-запросом к твоему backup: **во всех 77 строках
`vpn_keys` поле `host_name` равно константе `'GLOBAL'`**. Это не внешний
ключ на `xui_hosts.host_name`, вопреки более ранней версии кода. Значит
`keys.py` (`hosts.get(row["host_name"])`) никогда не находил хост ни для
одного ключа — `active_in_panel` и `subscription_url` были бы
`false`/`null` для абсолютно любого пользователя в проде.

Реальная структура (по анализу `key_email` в 77 реальных строках):
```
user@bot.local        -> локация A (без суффикса)
user-nl@bot.local      -> Нидерланды
user-us@bot.local      -> США
user-2@bot.local        -> ВТОРОЙ отдельный ключ того же пользователя
user-2_dev2@bot.local   -> дополнительное устройство ко второму ключу
```
Одна покупка = несколько строк `vpn_keys`, по одной на каждую локацию —
это и есть "единый VPN ключ на 4 локации с автобалансировкой" с сайта.
10 из 62 уникальных ключей в backup имеют такую тройку (остальные —
более старые ключи, видимо до появления мультилокационной выдачи).

Исправлено:
- `services/provisioning.py` [НОВОЕ] — покупка/продление выдаёт ключ на
  КАЖДОМ хосте из `xui_hosts` сразу (не жёстко на 4, а на всех активных —
  это и есть требуемая "если добавил страну — приложение само подхватит",
  но теперь применимо не только к списку серверов, а и к самой выдаче
  ключей).
- `routes/keys.py` — при чтении хост ключа ищется ЧЕСТНЫМ ПЕРЕБОРОМ по
  всем панелям 3x-ui (`xui_client.find_client_any_host`), а не по
  `host_name`, который для этого не годится. Строки группируются в одну
  визуальную "подписку" по общему префиксу `key_email` (`group_id` в
  ответе API).
- `services/xui_client.py` — добавлен общий кэш инбаундов на 120 сек
  (`get_all_inbounds_cached`), переиспользуемый и списком серверов, и
  статусами ключей — раньше каждый ключ на экране "Мои ключи" делал
  отдельный живой запрос к панели при каждом открытии экрана.

## 3. Триал был "выключен" по ошибке

`orders.py` v3 считал триал тарифом с `price == 0` в таблице `plans`.
В реальном backup таких строк нет (все 4 тарифа платные: 50/120/290/480 ₽).
Проверено: реальный триал настраивается в `bot_settings`
(`trial_enabled=true`, `trial_duration_days=2`) — отдельно от тарифов.
`menu_screen.dart` показывал пользователю неверный текст "триал не
настроен".

Исправлено: `POST /v1/orders/trial` читает `bot_settings` напрямую;
кнопка "Бесплатный период" в приложении реально его активирует.

## 4. Вход не совпадал с реальным сайтом

Проверено напрямую на vpnonline.su: сайт логинит по **email + паролю**
("Email адрес" / "Пароль" / "Войти в аккаунт"), код на почту используется
только для подтверждения регистрации и сброса пароля. Формат хэша в
backup — bcrypt (`$2b$10$...`). Версия auth.py v3 делала вход по
одноразовому коду — рабочий, но несовместимый с сайтом механизм: пароль,
который человек придумал на сайте, в приложении был бы вообще не нужен.

Исправлено: `routes/auth.py` переписан на email+пароль (bcrypt), плюс
отдельные `register/request-code` → `register/confirm` и
`password-reset/request-code` → `password-reset/confirm` — как на сайте.

**Синтетический telegram_id для веб-аккаунтов** — тоже проверено по
факту, не изобретено: в backup реальные веб/сайт-аккаунты имеют
ОТРИЦАТЕЛЬНЫЙ `telegram_id` (от −100009 до −100030), тогда как настоящие
Telegram-пользователи — большие положительные числа. `shop_db.create_web_user`
повторяет эту же схему (`MIN(telegram_id) − 1`, с retry на конфликт PK).

## 5. Реферальные проценты — из статичного текста в реальные данные

Сайт статично пишет "10% лифтайм / скидка другу 5%". Реальные значения в
`bot_settings` — **15% / 10%** (`referral_percentage`, `referral_discount`),
плюс `referral_on_start_referrer_amount=20` ₽ и `minimum_withdrawal=120` ₽.
Текст на сайте устарел относительно реально настроенных значений — если
захардкодить и в приложении, они разойдутся снова при следующем изменении
процента в панели. `routes/referral.py` и `referral_screen.dart` теперь
показывают то, что реально возвращает API.

## 6. Прочие исправленные баги (мельче, но реальные)

- `keys_screen.dart` читал несуществующие поля `keyData['id']` и
  `keyData['vless_uri']` (backend отдаёт `key_id` и `subscription_url`) —
  карточка ключа всегда показывала пустой ID и пустую ссылку.
  `devices_used` backend вообще не возвращает — блок "Устройства" не
  показывался никогда. Экран переписан под реальные поля + группировку
  по `group_id`.
- `ApiException` [НОВОЕ] — ошибки API долетали до UI как сырой
  `Exception('API error 409: {"detail":"..."}')` — пользователь видел бы
  JSON вместо текста. Теперь текст ошибки достаётся из поля `detail`.
- `plans_screen.dart`/`servers_screen.dart` — покупка больше не требует
  выбора сервера (см. пункт 2); экран "Серверы" стал информационным.

## Что не менялось (уже было верно в v3, перепроверено)

- Идемпотентность вебхуков через `processed_webhooks` — верно.
- Перепроверка оплаты YooKassa через её API, HMAC-подпись CryptoBot — верно.
- Мульти-хостовая работа с 3x-ui (сессии/куки отдельно на хост) — верно,
  дополнительно оптимизирована общим кэшем инбаундов (см. пункт 2).
- Параметризованные SQL-запросы везде — верно, не менялось.

## Известные ограничения этой сессии (честно)

- Нет доступа к сети/Flutter SDK в этой среде → не удалось скомпилировать
  и запустить ни backend (нет `pip install fastapi/sqlalchemy`), ни
  Flutter-приложение. Все правки проверены статически: `python3 -m
  py_compile` на 100% файлов backend, ручная трассировка логики каждого
  изменённого маршрута, проверка баланса скобок во всех `.dart`-файлах.
  Перед продом нужно прогнать `flutter analyze`/`flutter test` и живой
  backend против тестовой копии БД.
- Суффикс локации для НОВЫХ ключей (`services/provisioning.py`) — рабочее,
  но не проверенное на реальной панели допущение (см. SECURITY.md).
- Отправка email-кодов не подключена (`print` вместо SMTP) — см.
  `.env.example`.
- Сам VLESS-туннель (нативный код Android/iOS/Windows) по-прежнему вне
  этого скелета — как и в v3, это отдельная немаленькая нативная работа.
