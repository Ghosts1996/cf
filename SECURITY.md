# Аудит безопасности — что проверено и исправлено

Всё перечисленное относится к backend-мосту (папка `backend/`).

## Исправлено

1. **Подделываемый токен авторизации.**
   Было: после входа выдавался токен вида `dev-token-{email}` — его мог
   написать вручную кто угодно, зная (или подобрав) чужой email, и
   получить полный доступ к чужому аккаунту. Это критическая уязвимость.
   Стало: подписанный JWT (HMAC-SHA256, секрет из `.env`), проверяется
   на каждом защищённом эндпоинте через `app/auth_deps.py`.

2. **Вебхуки платежей без проверки подлинности.**
   Было: статус платежа брался прямо из тела входящего запроса. Любой,
   кто узнал URL вебхука, мог прислать поддельное "оплата прошла" и
   получить ключ бесплатно.
   Стало: для YooKassa — перепроверка статуса напрямую через её API по
   `payment_id` (тело вебхука используется только как триггер "проверь
   такой-то платёж", не как источник истины). Для CryptoBot — проверка
   HMAC-подписи заголовка `Crypto-Pay-API-Signature` по их официальной схеме.

3. **Отсутствие идемпотentности вебхуков.**
   Было: повторная доставка одного и того же вебхука (провайдеры это
   делают при таймаутах/ретраях) могла бы выдать/продлить ключ дважды.
   Стало: перед выдачей проверяется `order.status == "fulfilled"`.

4. **Цена заказа теоретически могла быть скомпрометирована** при
   дальнейшей доработке (если бы кто-то по невнимательности добавил
   `amount` в тело запроса от клиента). Явно зафиксировано: цена ВСЕГДА
   вычисляется на сервере из `PLANS` по `plan_id`, клиент не передаёт сумму.

5. **Перебор кода подтверждения email.**
   Было: не было лимита попыток ввода 6-значного кода.
   Стало: максимум 5 попыток, затем код сгорает; плюс минимум 60 секунд
   между повторными запросами кода (защита от спама рассылкой).

6. **Утечка платёжных данных в логи.**
   Было: `print(body)` на вебхуках печатал весь payload (потенциально
   включая платёжные метаданные) в консоль/логи процесса.
   Стало: убрано; логируются только факты уровня "заказ X выполнен".

7. **SQL-инъекции.** Весь доступ к общей БД бота (`shop_db.py`) сделан
   через параметризованные запросы SQLAlchemy (`text(...)` с bind-параметрами),
   без склейки строк — это единственный безопасный способ.

## Не исправлено — требует доступа к боевой среде

- **Реальная схема таблиц бота.** `shop_db.py` и `xui_client.py` содержат
  предположения об именах таблиц и колонок, помеченные комментариями. Их
  нужно свести с реальной схемой — иначе SQL не найдёт данные (упадёт с
  понятной ошибкой, а не отдаст тихо неверный результат).
- **Доступ к админ-панели.** Она открывается по прямому URL
  (`api.vpnonline.su/settings`) — нужно убедиться, что там есть авторизация
  (basic auth или IP-allowlist на уровне nginx как минимум).
- **Rate limiting на уровне сети** (защита от DDoS/брутфорса на сам
  сервер, не на конкретный эндпоинт) — это делается на реверс-прокси
  (nginx/Cloudflare), не в коде приложения.
- **Реальное тестирование на устройствах/пентест.** Всё выше — код-ревью
  логики, а не полноценный пентест боевого окружения. Перед продакшеном
  стоит прогнать через `pip-audit`/`safety` (зависимости) и, в идеале,
  сторонний security review, если оборот через приложение станет заметным.

## Что делает Flutter-клиент правильно уже сейчас
- Токен передаётся только в заголовке `Authorization: Bearer`, не в URL
  (не попадёт в логи веб-сервера/прокси).
- Секреты провайдеров нигде не встроены в клиентский код — все ключи
  живут только в `backend/.env` на сервере.

# v4 — новые находки и исправления (по реальному backup БД и реальному сайту)

Всё ниже проверено напрямую по `users-20260803-134623.db` и по
vpnonline.su, а не предположено. Полный разбор — в CHANGELOG.md.

## Критические функциональные баги (не про безопасность, но без этого
## ничего не работало) — исправлено

1. **В приложении не было ни одного экрана входа**, и `ApiClient`
   создавался заново на каждом экране без токена — весь функционал
   синхронизации (баланс/ключи/покупка/рефералка) физически не мог
   работать. Добавлен `auth_screen.dart` + единый `ApiClient.instance` с
   токеном в защищённом хранилище (`flutter_secure_storage` — Keychain/
   Keystore/Credential Manager, не SharedPreferences).
2. **`vpn_keys.host_name` в реальной БД — всегда константа `'GLOBAL'`**,
   не внешний ключ на `xui_hosts`. Код, писавший `hosts.get(row["host_name"])`,
   гарантированно не находил хост ни для одного ключа в проде —
   `active_in_panel` и `subscription_url` были бы `false`/`null` всегда.
   Исправлено перебором по всем панелям (`xui_client.find_client_any_host`).
3. **Покупка требовала выбор одного сервера**, хотя реальный продукт
   выдаёт ключ сразу на всех локациях бандла (подтверждено и текстом
   сайта, и структурой реальных `vpn_keys`). Переделано на
   `services/provisioning.py` — покупка выдаёт ключ на каждом активном
   хосте `xui_hosts` сразу, включая только что добавленные (это и есть
   требуемая автосинхронизация новых стран).
4. **Триал считался несуществующим** — код искал тариф с `price == 0` в
   `plans`, такого там нет. Реальный триал живёт в `bot_settings`
   (`trial_enabled`/`trial_duration_days`). Исправлено, плюс добавлен
   публичный эндпоинт `/v1/settings` для этих и реферальных значений.
5. **Вход не совпадал с сайтом.** Сайт логинит по email+паролю (bcrypt),
   а не по одноразовому коду. Переделано: `auth.py` теперь email+пароль
   для входа, код на почту — только для регистрации и сброса пароля, как
   на сайте.

## Проверки безопасности для v4-кода

- **Пароли** — только `bcrypt.checkpw`, хэш никогда не хранится в открытом
  виде и не сравнивается напрямую.
- **Brute-force по паролю** — новая поверхность атаки, которой не было в
  v3 (там пароля не было вообще). Добавлен лимит: 10 неверных попыток на
  email за 15 минут.
- **Email enumeration** — ответы `register/request-code` и
  `password-reset/request-code` НЕ отличаются в зависимости от того,
  существует ли email в базе (иначе можно перебором узнать, кто
  зарегистрирован).
- **Гонка при регистрации** — `email` не UNIQUE на уровне схемы БД бота;
  добавлена повторная проверка прямо перед вставкой пользователя.
- **Синтетический telegram_id для веб-аккаунтов** — выделяется с retry-циклом
  на конфликт PRIMARY KEY (защита от гонки двух одновременных регистраций).
- Секретные ключи `bot_settings` (токены ботов, пароли панелей, ключи
  платёжных систем) **сознательно исключены** из нового публичного
  `/v1/settings` — явный whitelist полей в `shop_db.get_public_settings()`,
  а не blacklist (безопаснее: новое поле в bot_settings по умолчанию НЕ
  становится публичным).

## Допущение, которое стоит проверить перед продом

`services/provisioning.py` определяет суффикс локации для новых ключей по
country_code из remark инбаунда (`-de`, `-nl`, `-us`, `-ru`). Это совпадает
с фактическим суффиксом существующих ключей для Нидерландов и США, но на
живой панели не проверялось. Влияет только на имя ключа в 3x-ui — чтение
(`routes/keys.py`) от суффикса не зависит и работает перебором в любом
случае. Стоит прогнать одну тестовую покупку на стейджинге.

## Проверено статически, требует прогона на стенде

- Правки backend проверены `python3 -m py_compile` и трассировкой логики
  каждого изменённого маршрута. Перед продом нужен `flutter analyze` и
  `flutter test`, а также прогон backend с боевым `.env` против тестовой
  копии БД.
- Ответ панелей 3x-ui на `addClient`/`updateClient` может отличаться между
  форками — см. пометки "ПРЕДПОЛОЖЕНИЕ" в `xui_client.py`.
- Отправка писем с кодами подтверждения не подключена (`print` вместо
  SMTP): без неё регистрация и сброс пароля не работают у живых
  пользователей.

# Патч бэкенда shopbot (`backend-patch/`)

Правки к `api.py` и `database.py` реального бота.

1. **Пароль от почты рассылки в исходном коде.** `GMAIL_APP_PASSWORD` имел
   рабочее значение по умолчанию прямо в тексте программы. Теперь пароль
   берётся только из переменной окружения; без неё письмо не отправляется и
   это логируется как ошибка. Сам пароль нужно считать скомпрометированным
   и отозвать в Google Account → Security → App Passwords.
2. **Публичный API-ключ по умолчанию.** Без `SHOPBOT_API_KEY` в `.env`
   ключом становилась общеизвестная строка из открытого форка. Теперь
   сервер отвечает 500, а сравнение ключа идёт через `hmac.compare_digest`.
   Ключ всё равно виден в APK после декомпиляции — он отсекает случайных
   ботов, а не целевую атаку; конкретного пользователя защищает токен
   сессии.
3. **Email-enumeration на восстановлении пароля.**
   `/auth/reset-password/send-code` отвечал 404 для незарегистрированного
   email. Теперь ответ одинаковый (`{"ok": true}`) независимо от того,
   существует ли аккаунт; письмо уходит только существующему.
   `/auth/register/send-code` намеренно оставлен с 409 — распространённый
   компромисс ради UX регистрации.
4. **Гонка при списании баланса (TOCTOU).** В `/key/create`, `/key/extend`
   и `upgrade_key_devices()` баланс проверялся одним запросом, а списывался
   другим: два параллельных запроса могли пройти проверку и списать
   дважды, уведя баланс в минус. Все три места переведены на атомарную
   `deduct_from_balance()` (она уже была в коде, просто не использовалась)
   с возвратом денег, если провижининг на XUI не удался после списания.
5. **PII в логах.** Полные email писались в логи открытым текстом —
   добавлена маскировка (`ab***@example.com`), а для лога о смене пароля
   пишется telegram_id. Ротация самих файлов логов — настройка окружения
   (logrotate), не код.
6. **Коды подтверждения и счётчик писем перенесены из памяти процесса в
   SQLite** (таблицы `verification_codes`, `email_send_log`, атомарный
   рейт-лимит через `BEGIN IMMEDIATE`) — работает при любом числе воркеров
   Flask.

Известный риск, который патч не закрывает: `xui_hosts.host_pass` и
SSH-пароли хранятся в БД открытым текстом — иначе бот не сможет логиниться
в панель. Доступ на чтение `users.db` означает доступ ко всем панелям 3x-ui;
если файл БД покидал сервер, пароли стоит ротировать. Шифрование at rest
или вынос в секрет-хранилище — отдельная задача.
