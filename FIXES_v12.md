# v12 — реальные фиксы по твоим 3 пунктам (16 авг 2026)

Проверено чтением всего кода (app/lib, android/, backend-patch/), сверено с
реальной подпиской (curl на твой sub-URL — стандартный 3x-ui base64 список
vless://, ничего экзотического) и с реальным README пакета
`flutter_singbox_client` (pub.dev, автор amirzr.dev, GPL-3.0, latest 1.1.0 —
версия в pubspec.yaml `^1.1.0` совпадает, `flutter pub get` не должен упасть
на резолве версии).

## 1. "Ключ с наибольшим сроком аренды" — было НЕ так
`connect_screen.dart::_loadKeyState()` брал `active.first` — первый активный
ключ в том порядке, в котором его вернул бэкенд (обычно по дате покупки, не
по остатку срока). Если у аккаунта несколько ключей — мог подключиться не к
тому. **Исправлено**: список активных ключей теперь сортируется по
`expiry_date` по убыванию, берётся первый (= самый долгоживущий).

## 2. "0 приём / 0 отдача" — было наполовину исправлено, наполовину — новый риск
Ядро уже было переключено с Xray-core на sing-box (`flutter_singbox_client`)
в предыдущей версии — это была ПРАВИЛЬНАЯ и подтверждённая мной находка
(реальный issue: VLESS+Reality от 3x-ui систематически не поднимается на
Xray-core based клиентах, но работает на sing-box, как в Hiddify).

НО: при выполнении твоего пункта 3 ("DPI и DNS выключены по умолчанию") я
обнаружил, что `_buildSingBoxConfig()` включал блок `dns` целиком ТОЛЬКО
если тумблер "DNS-защита" включён — а маршрут `{'protocol':'dns',
'outbound':'dns-out'}` применяется всегда безусловно. Если бы я просто
поменял fallback на `false` и не тронул остальное — это гарантированно
вернуло бы тот же самый "0 МБ" баг, только на sing-box и сразу при первом
запуске (тумблер ведь по умолчанию выключен). **Исправлено правильно**:
блок `dns` теперь есть всегда; тумблер переключает не "работает/не
работает", а МАРШРУТ резолва — `direct` (мимо туннеля, по умолчанию) или
`proxy` (через туннель, при включённой защите).

## 3. DPI/DNS выключены по умолчанию
Было `fallback: true` в трёх местах (tunnel_service.dart::connect(),
settings_screen.dart, security_screen.dart) — то есть оба работали "из
коробки" у пользователя, который их никогда не открывал в настройках, хотя
UI по умолчанию (в SecurityScreen) тоже рисовал их как `true`. Исправлено
консистентно во всех трёх местах на `false` — соответствие между тем, что
видит пользователь в UI при первом запуске, и тем, что реально уходит в
конфиг sing-box, теперь одно и то же.

## Бонус-находка — "визуал без функционала"
SplitTunnelScreen (экран "какие приложения идут в обход VPN") сохранял
выбор в LocalPrefs, но `TunnelService` его никогда не читал — переключатели
ничего не делали с реальным трафиком. Подключил: список пакетов теперь
передаётся в sing-box как `exclude_package` на tun-инбаунде (см.
sing-box.sagernet.org/configuration/inbound/tun/) при каждом `connect()`.
Ограничение (честно): применяется только при (пере)подключении, не на лету
к уже поднятому туннелю — это ограничение самого sing-box tun inbound
(список пакетов фиксируется при поднятии интерфейса), не баг реализации.

## Что НЕ трогал (не входило в запрос, честно фиксирую)
- `PrefKeys.splitTunnelMode` ('exclude'/'include') объявлен в local_prefs.dart,
  но нигде не используется — сейчас работает только режим "exclude" (выбранные
  явно идут в обход, всё остальное — в туннель). Если нужен режим
  "include" (в туннель — только выбранные) — это отдельная, более крупная
  правка UI + конфига (`include_package` вместо `exclude_package`).
- Секреты (backend GMAIL_APP_PASSWORD, SHOPBOT_API_KEY) — уже были вычищены
  в предыдущей сессии (см. backend-patch/REPORT.md), не трогал повторно.
- Разбор самой подписки (`_parseSubscriptionBody`, `_ParsedVless.tryParse`)
  проверен на твоём РЕАЛЬНОМ sub-URL построчно — работает корректно как
  есть, менять не пришлось.

## Не проверено (честно — нет сети/Android SDK в этой песочнице)
- Реальная компиляция `flutter build apk` и установка на устройство.
- Точные названия enum `ServiceState`/полей `TrafficStats` пакета
  `flutter_singbox_client` — сопоставлены по `toString()`-эвристике (см.
  комментарий в шапке tunnel_service.dart), это единственное место, которое
  может потребовать точечной правки после первого `flutter pub get` + сборки,
  если конкретные имена в установленном пакете разойдутся.
